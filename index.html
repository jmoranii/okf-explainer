THE OPEN KNOWLEDGE FORMAT, EXPLAINED WITH A BIKE SHOP

A folder that knows what it knows

The Open Knowledge Format (OKF) is a small open standard for writing down what an organization knows, so that people and AI agents can both read it. It is a folder of plain text files, each with a short header. Version 0.2 adds the part that matters once agents start writing those files: who wrote each page, who checked it, and whether it is still true.

This page walks through the format with a made-up bike shop, Halfway Cycles, and nothing that depends on one vendor's tools.

On this page

    Why write it down this way

    Most of what an organization knows lives in people's heads, in a wiki nobody trusts, or inside a tool that only that tool can read. OKF's bet is that a folder of plain text pages does the job better. §1 Here are six reasons, each with the part of this page that shows it.

    Plain text, nothing to install

    Every page is a text file. Any editor opens it today, and any editor will open it in twenty years.

    Start with one page

    People and models read the same page

    There is no export step and no second copy to fall behind. An agent loads the file as it is, and so do you.

    A folder an agent can walk

    Organized, and findable as it grows

    Folders, listings and links let a reader reach one page among thousands without opening the rest.

    What goes in the folderA folder an agent can walk

    It keeps up as things change

    An agent can draft pages and update them. Each page can say who wrote it, who checked it and when it expires, so a reader knows how far to trust it.

    Portable, with no lock-in

    A bundle is a folder. Copy it, zip it, or move it to another tool. No vendor's service stands between you and what you wrote.

    Versioned, so a team stays in step

    Kept in git, every change is recorded with who made it and why, and everyone works from the same copy.

    Start with one page

    OKF calls each page a concept. A concept can describe something you could point at, like a database table, or an idea, like how the shop defines a number. This one defines how long a repair takes.

    Try itSelect any line to see what it is for.

    metrics/turnaround-time.md

    Only one line is required: type. A page with a header that says what kind of thing it is, and nothing else, already conforms. §11 Everything else is there because it earns its place, and you add it when you need it.

    What goes in the folder

    The whole folder is called a bundle. You can organize it however suits the subject. The shop sorts its pages into tables, metrics, computations, playbooks and policies, and OKF has no opinion about those names or how deep they go. §3

    Around the pages sit four small files that do the housekeeping. Two are OKF's own: it reserves their names, and both are optional. §3.1 Two are older habits that sit comfortably beside it.

      The index is what keeps an agent from reading everything. It reads the top listing, picks a folder, reads that folder's listing, and opens the one page it needs.

A link is an ordinary markdown link, and the sentence around it says what the relationship is: this metric is computed from that table, this playbook follows that policy. §6.1 An agent uses both. The listings get it to the right page, and a link in that page takes it to the next one.

        Who wrote it, who checked it, and is it still true
        
    
        
      
        A folder that agents keep rewriting raises questions a plain note never had to answer. Version 0.2 answers them with three header lines. generated says who or what wrote the page. verified lists who has checked it against its sources. stale_after is the date after which nobody should take it on faith. §5
        
      
        A reader works out a trust level from verified alone. No entry means unverified. Entries from machines only means machine-confirmed. Any entry from a person means human-reviewed. Staleness is a separate question: a page the owner signed off in January can still be out of date by September.

          Letting an agent write the first draft
          
    
          
      
          Nobody wants to write two hundred of these pages by hand. The OKF repository includes a sample agent that drafts a bundle for you. Its example reads a Google BigQuery database, but the shape of the work is not tied to any product.
          
      
          The agent asks a source three things: what do you have, tell me about this one, and show me a little of it. Then it writes one page per thing it found. A second pass reads the documentation around the source and decides, page by page, whether to add to an existing concept, write a new reference page, or skip it.                   Then someone has to keep it current
                  
    
                  
      
                  A first draft is the easy part. Prices change, tables gain columns, and a folder nobody tends is wrong within a year. The specification expects agents to keep rewriting these pages, not to write them once. §1
                  
      
                  Plain text is what makes that workable. A person and a model read the same file, so the model does the bookkeeping and the person reads what changed. Keep the folder in git, on GitHub or anywhere else, and each change arrives as a diff with a name and a date on it. A team stays in step the same way: everyone, and every agent, sends changes to one shared copy, and git flags the collisions. The specification recommends git, names no host, and requires neither. §3

                    What a reader sees after this commit
                      
        
                      
        
                      
          
                      
            
                      
            
                      
          
                      
          
                      
        
                      
      
                      
      
                      A commit is one saved set of changes in git. Lines marked + were added and lines marked − were removed. “Edited since its check” is not an OKF trust level. It is what a careful reader works out by comparing the two dates in the header.
                      
    
                      
    
                      
      
                      Notice what the agent left alone: the sign-off and the expiry date. Nothing in OKF stops an agent from rewriting them. The format records who wrote a page and who checked it, and leaves the question of who is allowed to do which to you. §5.2 That is why the rule sits in the shop's AGENTS file and not in the specification.
                      
      
                      The review cost Mara one screen. She read two short diffs, not the whole folder, and her approval is a commit like any other: dated, attributed, and easy to undo.
                      
    
                      
  
                      

                      



                      
  
                      
    
                      A number that can show its work
                      
    
                      
      
                      Definitions are one problem. Numbers are a harder one. Ask an agent how long repairs took last month and it can write its own query, get a believable answer, and be wrong.
                      
      
                      OKF's answer is a page type called an Attested Computation. It holds the approved calculation and names the blanks an agent may fill in. The agent supplies values for the blanks and nothing else. Then a small piece of ordinary code, with no AI in it, checks two things: that what actually ran is the approved calculation with only the blanks filled in, and that the number on screen is the one that run produced. §10 §10.5

                      Checking a page and checking a run are different jobs, and the format keeps both. verified says the definition was checked and found right, by a person or by a process. Attestation says this particular run used that definition. §10.6
                      
      
                      The format records the calculation and how to check it. It does not run anything itself, and version 0.2 leaves the details of how receipts and verdicts travel to a later revision.
                      
    
                      
  
                      

                      



                      
  
                      
    
                      What it leaves out on purpose
                      
    
                      
      
                      Most of OKF's usefulness comes from how little it insists on. Non-goals
                      
    
                      
    
                      
      
                      
        
                      No official list of types
                      You name your own. A shop has playbooks and policies; a lab has protocols; a household has appliances and accounts.
                      
        
                      No required software
                      No server, database, or query language. A text editor and a folder are enough, and version control is recommended, not demanded.
                      
        
                      No replacing what you have
                      It points at your database schemas and documents. It does not try to become them.
                      
        
                      No strict gatekeeping
                      A reader must not reject a bundle for unknown types, extra header lines, broken links, or a missing index.
                      
      
                      
    
                      
    
                      
      
                      What teams add on top
                      
      
                      Most teams layer house rules over the format: a fixed list of page types, a check date on single facts instead of whole pages, a rule that the log is only ever added to, a line saying which of two overlapping pages wins. None of that is in the specification, and none of it breaks it. It helps to know which rules are OKF and which are yours.
                      
    
                      
  
                      

                      



                      
  
                      
    
                      Point an agent at what you have
                      
    
                      
      
                      You do not write the first pages by hand. You read them. The steps are the ones from the first-draft section, with your own source in place of the bike shop's.
                      
    
                      
    
                      
      
                        
        
                      1. Pick one source people keep asking you about: a database, a shared drive, a codebase, a wiki.
                        2. 
        
                      2. Give an agent read access to it, and the brief below. Any capable agent will do. The format does not care which.
                        3. 
        
                      3. Read what comes back. Fix what is wrong, then add a verified line to each page you would stand behind, and a stale_after date to anything that expires on a schedule, like prices.
                        4. 
        
                      4. Put the folder in git and write your house rules into an AGENTS file. From then on an update is a diff to read, not a rewrite.
                        5. 
      
                      
      
                      
        
                      brief for the agent
                      
        
                      Draft an Open Knowledge Format (OKF v0.2) bundle from the source I have given you access to.

1. List what the source contains, and tell me what you found before you write anything.

2. For each thing worth describing, write one markdown file with a YAML header: type, title, a one-sentence description, and generated: { by: your name and version, at: the time now in UTC }.

3. In the body, say what it is and how it is used. Link to related pages with ordinary markdown links. Do not invent details. Where you are unsure, say so on the page.

4. List where each page's content came from under sources in the header. Every entry needs a resource: the URL or path of the thing you read. For something too broad to point at, such as all the queries run against a table, state its scope in words.

5. Do not add a verified line. A person does that after reading.

6. When the pages are done, write an index.md in every folder, one line per page using its description, and start a log.md with today's date as the first heading.

The specification is at https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md
Follow it wherever this brief is silent.
